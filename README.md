# Pinhead Constructor

Конструктор одежды с принтом для [studio.pnhd.ru](https://studio.pnhd.ru): выбор изделия и цвета, загрузка картинки,
текст, перед/спина/рукава, расчёт цены со скидкой за тираж, заявка с номером заказа, PDF, превью и файлами печати.

```bash
npm install
cp .env.example .env.local
npm run dev        # http://localhost:3100/constructor
```

## Переменные окружения

| Переменная | Где нужна | Что делает |
|---|---|---|
| `NEXT_PUBLIC_PNHD_API_URL` | браузер | API каталога. По умолчанию `https://api.pnhd.ru` |
| `NEXT_PUBLIC_YM_COUNTER_ID` | браузер | Номер счётчика Яндекс.Метрики. Пусто — события пишутся в консоль |
| `NEXT_PUBLIC_PRICE_SOURCE` | браузер | Прайс DTF: `tiered` (по умолчанию, со скидкой за тираж) или `site` (таблица с главной) |
| `ORDER_BITRIX_WEBHOOK` | сервер | Входящий вебхук Битрикс24 с правами CRM. Задан — заявка создаёт сделку с файлами |
| `ORDER_BITRIX_CATEGORY_ID` | сервер | id воронки сделок. Пусто — воронка по умолчанию |
| `ORDER_TELEGRAM_BOT_TOKEN`, `ORDER_TELEGRAM_CHAT_ID` | сервер | Чат для заявок: используется, если Битрикс не задан или недоступен |
| `ORDER_BITRIX_SOURCE_ID` | сервер | Код источника сделки из справочника «Источники» CRM. Заведите источник «Конструктор» и укажите его код — по нему заявки отбираются фильтром и в отчётах |
| `ORDER_BITRIX_MARK_FIELD` | сервер | Необязательно: код своего поля сделки (`UF_CRM_…`), в которое пишется «Конструктор» |
| `ORDER_STORE_DIR` | сервер | Папка, где сервер хранит заявки до доставки в канал. По умолчанию `data/orders`. Должна переживать перезапуск (в Docker — том) |
| `NEXT_PUBLIC_POLICY_URL` | браузер | Ссылка на политику обработки персональных данных: показывается в согласии в форме заявки и в уведомлении о cookie |

Если не задан ни один канал, заявка пишется в лог сервера и остаётся в `ORDER_STORE_DIR` — так удобно проверять локально.

## Надёжность заявок

Сервер сначала сохраняет заявку с файлами на диск (`ORDER_STORE_DIR`), потом отправляет в канал. Если канал не ответил,
клиент всё равно получает номер заказа, а сервер повторяет отправку сам: через 1, 2, 4… минут, не реже раза в час.
После доставки файлы и контакты клиента с диска удаляются, остаётся короткая запись (номер, сумма, канал) на 30 дней.
Повторная отправка той же заявки из браузера (сбой сети, двойное нажатие) второй сделки не создаёт.
К заявке прикладывается `design.json` — слои с положением, размерами и шрифтами: по нему макет можно собрать заново.
Переменные `NEXT_PUBLIC_*` подставляются при сборке: после их изменения нужна пересборка.

Заявка уходит одним запросом со всеми файлами (превью, файлы печати, исходники, PDF) — это несколько мегабайт.
На хостингах с пределом размера запроса (например, 4,5 МБ у серверных функций Vercel) большие заявки
не пройдут: нужен хостинг без такого предела либо отдельная загрузка файлов.

## Демо-стенд (GitHub Pages)

При каждом пуше в `main` workflow `.github/workflows/pages.yml` собирает статическую версию
(`STATIC_EXPORT=1`, `NEXT_PUBLIC_DEMO=1`, `NEXT_PUBLIC_BASE_PATH=/<имя репозитория>`) и публикует её на GitHub Pages.
В демо нет серверной части: номер заказа выдаётся в браузере, заявка никуда не отправляется, экран успеха и PDF работают.
Стенд открывается по адресу `https://<владелец>.github.io/<репозиторий>/` и сам переходит на `/constructor/`.

## Автотесты

```bash
npx playwright install chromium webkit   # один раз
npm run test:e2e
```

Playwright сам поднимает сервер на порту 3111 в отдельной папке сборки (`.next-e2e`), с выключенными каналами заявок
и своим хранилищем `data/e2e-orders` — рабочему dev-серверу не мешает, тестовые заявки никуда не уходят.
Проверяется: сценарий «картинка → размеры → заявка → номер» на 1440 px, 375 px и в Safari (WebKit); повторная
отправка без дубля; запрет заявки с принтом за границей зоны; файл печати — размер в пикселях против сантиметров
и положение элементов против превью. Каталог берётся из живого API, без сети тесты не пройдут.

## Cookie и аналитика

На стенде при заданном `NEXT_PUBLIC_YM_COUNTER_ID` показывается уведомление о cookie с кнопкой «Отказаться».
После отказа счётчик не загружается, события конструктора не отправляются (ключ `pinhead_analytics_off` в localStorage).
При встраивании на сайт уведомление — своё у сайта; чтобы конструктор уважал отказ, сайт выставляет тот же ключ.
В режиме разработки счётчик не загружается.

## Цели Метрики

Чтобы события попали в отчёты, цели типа «JavaScript-событие» должны быть заведены в счётчике:
`design_upload`, `order_submit`, `order_send_error`, `pdf_download`, а также `constructor_open`, `garment_select`,
`color_select`, `text_add`, `side_switch`, `size_set`, `order_form_open`, `order_send`.

Устройство модуля — `docs/ARCHITECTURE.md`.
Как менеджеру читать заявку и проверять файл печати — `docs/MANAGER-GUIDE.md`.
